<Callout>
Você tem um milhão de elementos e uma enxurrada de perguntas intercaladas: "estes dois estão no mesmo grupo?" e "junte estes dois grupos". Refazer uma busca em grafo a cada pergunta custa O(V+E) **por pergunta**. O **Union-Find**, também chamado de **Disjoint Set Union (DSU)**, responde as duas em tempo praticamente constante usando dois arrays de inteiros e um punhado de linhas de código. O preço é uma limitação brutal, e é ela que compra o desempenho: ele funde grupos e **nunca** os separa de volta.
</Callout>

## O buraco: perguntar e juntar, um milhão de vezes

Imagine uma rede social com 200.000 pessoas. Chegam 200.000 operações misturadas, em ordem imprevisível:

- `conectar(a, b)`: descobrimos que `a` e `b` são amigos.
- `mesmo_grupo(a, b)`: `a` e `b` estão na mesma bolha de amizades, direta ou indiretamente?

A segunda pergunta é sobre **conectividade**, não sobre adjacência: `a` e `b` podem estar a doze apertos de mão de distância e a resposta ainda é sim. A primeira ideia é o [DFS/BFS](/topico/dfs-bfs): a cada pergunta, saia de `a` e veja se `b` aparece. Correto e desesperador. Cada busca é O(V+E), e 200.000 perguntas sobre um grafo com 200.000 arestas dão na casa de 10¹⁰ passos. O trabalho é refeito do zero toda vez, e nada do que a busca anterior descobriu é aproveitado.

A segunda ideia é boa: guarde um **rótulo de grupo** por elemento, num array. A pergunta vira `rotulo[a] == rotulo[b]`, O(1), imbatível. O problema mudou de lado: agora a **união** é que dói. Fundir dois grupos exige varrer o array e reetiquetar todo mundo de um deles. O(n) por união.

A terceira ideia conserta a segunda pela metade: mantenha, além dos rótulos, uma [tabela hash](/topico/hash-table) de grupo para lista de membros, e na hora de unir **reetiquete sempre o grupo menor**. Cada elemento só muda de rótulo quando o grupo dele pelo menos dobra de tamanho, e dobrar só acontece log₂ n vezes. Total O(n log n), o que já é aceitável, ao custo de manter as listas de membros na memória e copiar elementos de verdade.

Guarde essa terceira ideia, porque **o Union-Find é ela sem a cópia**. Em vez de mover os elementos do grupo menor, ele move um ponteiro só: a raiz do grupo menor passa a apontar para a raiz do maior. Um inteiro escrito, e o grupo inteiro trocou de dono.

| Estratégia | "mesmo grupo?" | "junte os grupos" | O que ela guarda |
| --- | --- | --- | --- |
| Refazer DFS/BFS | O(V+E) | O(1), só anotar a aresta | lista de adjacência |
| Rótulo de grupo num array | O(1) | O(n), reetiquetar tudo | um array de n inteiros |
| Rótulo + reetiquetar o menor | O(1) | O(log n) amortizado, copiando | array + listas de membros |
| **Union-Find** | **O(α(n))** | **O(α(n))** | **dois arrays de n inteiros** |

Aquele `α(n)` é a inversa da função de Ackermann: para qualquer `n` que caiba neste universo, ele vale no máximo 4.

## A floresta que mora dentro de um array

Cada conjunto vira uma **árvore**. O elemento na raiz é o **representante** do conjunto, e é só isso que ele significa: um crachá arbitrário, sem valor semântico nenhum. A pergunta "vocês dois são do mesmo grupo?" vira "vocês dois sobem até a mesma raiz?".

O conjunto de todas essas árvores é uma **floresta**, e aqui está o pulo do gato: essa floresta **não existe** como estrutura de dados. Não há classe `No`, não há ponteiro para filho, não há alocação. Há um [array](/topico/arrays) de inteiros chamado `pai`, e a árvore é o desenho que ele sugere.

```
índice     0    1    2    3    4    5    6
pai     [  0,   0,   1,   1,   4,   4,   4 ]
           ^                   ^
           raiz (pai[0] == 0)  raiz (pai[4] == 4)

         0                4          conjunto {0,1,2,3}, representante 0
         |               / \         conjunto {4,5,6},   representante 4
         1              5   6
        / \
       2   3
```

Três coisas para reparar nesse desenho, porque as três derrubam gente:

<Colunas>
<Cartao titulo="A raiz aponta para si mesma">
`pai[x] == x` é a definição de "x é raiz". Não existe `None`, não existe sentinela. É o que faz o laço de subida ter uma condição de parada de graça, e é o que faz a inicialização caber numa linha: `pai = list(range(n))`, todo mundo sozinho no próprio grupo.
</Cartao>
<Cartao titulo="A seta só vai numa direção">
Do filho para o pai. Você **não** consegue listar os filhos de um nó sem varrer o array inteiro, e nunca vai precisar. Toda operação sobe, nenhuma desce. Metade da economia da estrutura vem daí.
</Cartao>
</Colunas>

A terceira: **a forma da árvore não tem significado nenhum**. Que o 2 seja filho do 1 e não filho do 0 não diz nada sobre os dados. É pura contabilidade interna, e é justamente por isso que a estrutura pode reorganizá-la à vontade, o que as otimizações fazem sem dó.

## O `find` ingênuo e a corrente que estraga tudo

A versão de manual tem duas funções e nenhuma esperteza:

```python
pai = list(range(n))          # cada elemento começa sendo a própria raiz

def find(x):
    while pai[x] != x:        # sobe até a raiz
        x = pai[x]
    return x

def unir(a, b):
    pai[find(a)] = find(b)    # a raiz de a passa a apontar para a raiz de b
```

Funciona, e o custo de tudo é a **altura da árvore**. O problema é que nada nesse código controla a altura. Considere a sequência mais natural do mundo, uma fila de dominós:

```
unir(0,1); unir(1,2); unir(2,3); ... unir(n-2, n-1)

pai = [1, 2, 3, 4, 5, 6, 6]

0 → 1 → 2 → 3 → 4 → 5 → 6
```

A floresta virou uma [lista encadeada](/topico/listas-ligadas), e `find(0)` numa corrente de 100.000 elementos custa exatamente **99.999 passos**. Medido, não estimado.

<Callout tipo="aviso">
Isso não é um caso adversarial exótico. É a ordem em que as arestas costumam chegar num arquivo de entrada, num caminho, numa linha de tempo. O pior caso do Union-Find ingênuo é o dado mais comum que existe.
</Callout>

E não pense que embaralhar salva. Com 200.000 elementos e 200.000 uniões de pares **sorteados**, a versão sem otimização nenhuma produziu uma árvore de **altura 20.270** e gastou **11.140 passos por `find`**, em média. Aleatoriedade não é balanceamento.

## As duas otimizações, uma de cada vez

São duas ideias independentes, e a diferença entre elas é onde agem: uma controla a forma da árvore na hora de **unir**, a outra conserta a forma na hora de **consultar**. Cada uma sozinha já leva o custo de O(n) para O(log n). Só as duas juntas chegam ao α(n).

### Union by size: a árvore menor entra embaixo da maior

A união ingênua escolhe o perdedor no cara ou coroa: quem foi passado como segundo argumento vira a raiz. Basta escolher direito: **a árvore com menos elementos entra embaixo da árvore com mais**.

```python
pai = list(range(n))
tamanho = [1] * n                     # quantos elementos há na árvore de cada raiz

def unir(a, b):
    ra, rb = find(a), find(b)
    if ra == rb:
        return False                  # já eram do mesmo grupo, nada a fazer
    if tamanho[ra] < tamanho[rb]:
        ra, rb = rb, ra               # ra é sempre a raiz da árvore MAIOR
    pai[rb] = ra
    tamanho[ra] += tamanho[rb]
    return True
```

A garantia sai de um argumento de duas linhas: a profundidade de um elemento só aumenta quando a árvore dele é pendurada embaixo de outra **pelo menos igual**, e nesse momento o grupo dele no mínimo dobra de tamanho. Um grupo só pode dobrar log₂ n vezes antes de conter todo mundo. Logo, **a altura nunca passa de log₂ n**: 20 para um milhão de elementos. Na medição com 200.000 elementos, a altura máxima caiu de 20.270 para **8**, e o custo médio de um `find` caiu de 11.140 passos para **1,85**.

### Union by rank: a mesma ideia contando andares

A variante clássica guarda, em vez do tamanho, o `rank`: um limite superior para a altura da árvore.

```python
rank = [0] * n                        # toda árvore de um nó só tem altura 0

def unir(a, b):
    ra, rb = find(a), find(b)
    if ra == rb:
        return False
    if rank[ra] < rank[rb]:
        ra, rb = rb, ra               # ra é sempre a raiz da árvore MAIS ALTA
    pai[rb] = ra
    if rank[ra] == rank[rb]:
        rank[ra] += 1                 # empate: a vencedora ganhou um andar
    return True
```

O limite é o mesmo, log₂ n, e o desempenho é indistinguível na prática. Duas observações honestas: **o `rank` deixa de ser a altura de verdade** assim que o path compression entra em cena, porque a compressão achata a árvore e ninguém atualiza o `rank` para baixo. Não é bug: ele continua sendo um limite superior válido, que é tudo de que a prova precisa. E **union by size tem um bônus**: você ganha de graça a resposta para "quantos elementos tem o grupo do `x`?", que vários problemas pedem. Por isso o resto deste artigo usa size.

### Path compression: achatar o caminho na volta

A segunda ideia ataca o outro lado. Se `find(x)` já pagou para subir até a raiz, é desperdício jogar esse caminho fora: **reaponte todo mundo do caminho direto para a raiz**. A próxima consulta a qualquer um deles custa um passo.

A forma mais curta é recursiva, e cabe em três linhas:

```python
def find(x):
    if pai[x] != x:
        pai[x] = find(pai[x])   # na VOLTA da recursão, todo mundo aponta para a raiz
    return pai[x]
```

A elegância aqui é que a compressão acontece de graça no desempilhamento: a chamada mais funda devolve a raiz, e cada nível que retorna grava essa raiz no próprio `pai`. É um dos exemplos mais limpos de "fazer o trabalho na volta" que a [recursão](/topico/recursao) oferece.

<Callout tipo="aviso">
Em Python essa versão é uma bomba-relógio. O limite padrão de recursão é **1.000**, e uma corrente de 10.000 elementos levanta `RecursionError: maximum recursion depth exceeded` (testado). Pior: a exceção estoura **antes** de a compressão consertar qualquer coisa, então o remédio nunca chega. Dá para levantar o teto com `sys.setrecursionlimit`, e no CPython 3.13 uma corrente de um milhão sobe sem reclamar, mas aí você amarra o código a um detalhe de versão do interpretador e paga um quadro de pilha por elo da corrente. Em competição e em produção, escreva iterativo.
</Callout>

A versão iterativa faz duas passadas: uma para achar a raiz, outra para reapontar.

```python
def find(x):
    raiz = x
    while pai[raiz] != raiz:      # primeira passada: onde é a raiz?
        raiz = pai[raiz]
    while pai[x] != raiz:         # segunda passada: reaponta o caminho inteiro
        proximo = pai[x]
        pai[x] = raiz
        x = proximo
    return raiz
```

E existe uma terceira forma, o **path halving**, que faz o serviço numa passada só apontando cada nó para o avô:

```python
def find(x):
    while pai[x] != x:
        pai[x] = pai[pai[x]]      # pula o pai, adota o avô
        x = pai[x]
    return x
```

Ela não achata tanto quanto as duas passadas (o caminho encolhe pela metade em vez de virar altura 1), mas tem a mesma garantia assintótica, escreve metade dos inteiros e dispensa a variável extra para guardar a raiz. É a que vai na implementação final deste artigo.

Sozinho, o path compression também conserta a corrente dos dominós, só que de um jeito diferente. Numa corrente já formada, o **primeiro** `find(0)` continua custando 99.999 passos, e todos os seguintes custam 1. É a definição de custo amortizado, e é por isso que a garantia do compression sozinho é amortizada e não vale por operação.

### As duas juntas

Os números abaixo são de uma medição real: 200.000 elementos, 200.000 uniões de pares sorteados, depois 400.000 chamadas de `find`, contando os passos de subida. A compressão medida aqui é a de duas passadas, e a altura é a da floresta **ao fim de tudo**: as consultas também achatam.

| Otimização | Altura máxima da floresta | Passos por `find`, em média |
| --- | --- | --- |
| Nenhuma | 20.270 | 11.140,45 |
| Só union by size | 8 | 1,85 |
| Só path compression | 4 | 1,20 |
| **As duas** | **3** | **0,96** |

Menos de um passo por consulta. A média fica **abaixo de 1** porque boa parte das chamadas cai num elemento que já é a raiz, ou está pendurado direto nela. E a garantia teórica, essa sim, precisa das duas juntas: só o size dá O(log n) por operação; só a compressão dá O(log n) amortizado; as duas em conjunto dão o famoso **O(α(n)) amortizado**, provado por Robert Tarjan em 1975 e estendido por Tarjan e van Leeuwen em 1984 ao conjunto todo de variantes, inclusive o par union by size mais path halving, que é o da implementação abaixo.

## O α(n): o que "praticamente constante" quer dizer

A função de Ackermann é o exemplo canônico de função que cresce absurdamente rápido. O `α(n)` é a inversa dela, e por isso cresce absurdamente devagar. Devagar assim:

| Faixa de n | α(n) |
| --- | --- |
| 0 a 2 | 0 |
| 3 | 1 |
| 4 a 7 | 2 |
| 8 a 2.047 | 3 |
| 2.048 até um número indescritível | 4 |

O tal número indescritível é uma torre de potências de 2 com cerca de dois mil andares: cada andar é 2 elevado ao andar de baixo, e a base é 2.047. Para calibrar: o universo observável tem cerca de 10⁸⁰ átomos, o que é aproximadamente 2²⁶⁶. O **primeiro** andar da torre já passa de 2²⁰⁴⁷, e faltam outros dois mil. **α(n) ≤ 4 para qualquer n que você consiga escrever.** Daí a prática universal de tratar Union-Find como O(1) e seguir a vida.

Mas duas ressalvas honestas, porque "praticamente constante" é uma frase que esconde coisa:

**É amortizado, não é pior caso por operação.** A garantia de Tarjan é sobre uma **sequência** de m operações: o total custa O(m · α(n)). Uma chamada individual de `find` pode muito bem custar O(log n): a primeira que sobe uma árvore alta paga a subida inteira e, de quebra, achata o caminho para as próximas. Em algoritmo de competição isso é irrelevante. Em sistema de tempo real com prazo por operação, não é. É a mesma conversa do array dinâmico que dobra de tamanho, na página de [Big O](/topico/big-o).

**O α não é folga na demonstração.** Fredman e Saks provaram em 1989 um limite inferior de Ω(α(n)) **amortizado por operação** para esse problema no modelo de cell probe. Ou seja: não existe uma análise mais esperta esperando ser descoberta, nem uma implementação que chegue a O(1) de verdade. O α é a resposta certa.

| Operação | Custo amortizado | Custo de uma chamada isolada |
| --- | --- | --- |
| `find`, `unir`, `conectado` | O(α(n)) | O(log n) |
| Construir com n elementos | O(n) | O(n) |
| Memória | 2n inteiros | não se aplica |

## A implementação completa

Esta é a versão para copiar. Union by size, path halving, contador de componentes, e o `unir` devolvendo se a fusão realmente aconteceu. Esse `bool` é o que faz metade dos problemas caírem.

```python
class UnionFind:
    __slots__ = ("pai", "tamanho", "componentes")

    def __init__(self, n):
        self.pai = list(range(n))      # todo mundo começa sendo a própria raiz
        self.tamanho = [1] * n         # só é válido NA RAIZ de cada árvore
        self.componentes = n           # n elementos soltos = n grupos

    def find(self, x):
        """A raiz do grupo de x, achatando o caminho na subida."""
        while self.pai[x] != x:
            self.pai[x] = self.pai[self.pai[x]]   # path halving: adota o avô
            x = self.pai[x]
        return x

    def unir(self, a, b):
        """Funde os grupos de a e b. Devolve False se já eram o mesmo grupo."""
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False
        if self.tamanho[ra] < self.tamanho[rb]:
            ra, rb = rb, ra                       # ra é sempre a árvore maior
        self.pai[rb] = ra
        self.tamanho[ra] += self.tamanho[rb]
        self.componentes -= 1                     # só aqui, e só quando uniu mesmo
        return True

    def conectado(self, a, b):
        return self.find(a) == self.find(b)

    def tamanho_do_grupo(self, x):
        return self.tamanho[self.find(x)]         # o find NÃO é opcional aqui
```

Trinta linhas, duas listas de inteiros, zero alocação de objeto. É uma das melhores relações entre potência e tamanho de código de toda a área, e é por isso que vale a pena decorá-la. O `find` dentro de `tamanho_do_grupo` não é enfeite: o array `tamanho` **só tem valor correto na raiz**, e em qualquer outro índice ele guarda o número que aquela árvore tinha quando parou de ser raiz. Plausível e errado, o pior tipo de erro.

## Onde o Union-Find aparece de verdade

O Union-Find é a estrutura das **relações de equivalência**. Sempre que a sua relação for reflexiva, simétrica e transitiva ("é amigo de", "é a mesma conta que", "é igual a", "está conectado a"), ela particiona o universo em classes, e essa partição é exatamente o que a estrutura mantém.

**[Árvore geradora mínima](/topico/mst) com Kruskal.** É o caso canônico, a ponto de dar para dizer que **Kruskal é ordenação mais Union-Find**. Ordene as arestas por peso e aceite cada uma que ligar dois grupos ainda separados:

```python
def kruskal(n, arestas):
    """arestas: lista de (peso, u, v). Devolve o custo e as arestas escolhidas."""
    dsu = UnionFind(n)
    total, escolhidas = 0, []
    for peso, u, v in sorted(arestas):
        if dsu.unir(u, v):          # False = os dois já estavam ligados, fecharia ciclo
            total += peso
            escolhidas.append((u, v))
    return total, escolhidas
```

O algoritmo inteiro é esse. O `if` faz o trabalho que uma verificação de ciclo faria, e o custo total passa a ser dominado pela [ordenação](/topico/merge-sort), O(E log E): o Union-Find some no ruído.

**Componentes conexos em grafo estático.** Contar quantas ilhas existem é ler as arestas e devolver `dsu.componentes`. É o LeetCode 547, *Number of Provinces*, quase literalmente. E o 1584, *Min Cost to Connect All Points*, é Kruskal disfarçado: o grafo é completo, o peso é a distância de Manhattan, e a resposta é a MST.

<Callout tipo="aviso">
Se o grafo é estático e você precisa dos componentes **uma vez só**, um [DFS/BFS](/topico/dfs-bfs) resolve em O(V+E) com código mais simples e provavelmente mais rápido. O Union-Find ganha quando as perguntas **se intercalam** com as uniões, porque aí a busca teria que ser refeita. Escolher DSU para um problema de uma passada só é complicar de graça.
</Callout>

**Detecção de ciclo em grafo não dirigido.** Se `unir(u, v)` devolve `False`, a aresta liga dois vértices que já estavam conectados: ela fecha um ciclo. É o LeetCode 684, *Redundant Connection*, resolvido em cinco linhas.

E aqui vai a fronteira que quase todo mundo cruza sem perceber: **isso não funciona em grafo dirigido**. O Union-Find não tem noção de direção: ele só sabe "mesmo grupo". Pegue as arestas `A→B`, `A→C` e `B→C`: não existe ciclo nenhum, mas na hora de processar `B→C` o DSU vai encontrar os dois já no mesmo grupo e gritar "ciclo". Para ciclo dirigido o caminho é [ordenação topológica](/topico/topological-sort), ou um DFS com marcação de três cores.

**Fusão de identidades.** O LeetCode 721, *Accounts Merge*, é o problema didático perfeito: cada e-mail é um elemento, dois e-mails que aparecem na mesma conta são unidos, e no fim cada grupo é uma pessoa. É literalmente o que sistemas de identidade fazem para reconciliar cadastros duplicados. Já o 990, *Satisfiability of Equality Equations*, é a relação de equivalência na forma mais crua possível: processe **todas** as igualdades primeiro, construindo os grupos, e só depois confira se alguma desigualdade `a != b` caiu dentro de um mesmo grupo.

**Sequências e percolação.** O LeetCode 128, *Longest Consecutive Sequence*, sai unindo `v` com `v+1` e devolvendo o maior `tamanho_do_grupo`. Vale escrever, embora a solução com [conjunto hash](/topico/hash-table) seja mais simples e igualmente O(n). E o experimento clássico de **percolação** (a partir de que fração de células abertas a água atravessa a grade?) é Union-Find com um truque bonito: dois nós virtuais, um ligado a toda a linha de cima e outro a toda a linha de baixo. A grade percola no exato instante em que os dois nós virtuais entram no mesmo grupo.

O que fica de fora dessa lista é tudo que depende de direção ou de estrutura interna do grafo: componentes fortemente conexos, pontes, pontos de articulação. Esse é o assunto de [Grafos Avançados](/trilha/grafos-avancados/), e a ferramenta lá é o DFS com lowlink, não o Union-Find.

## A limitação que define a estrutura: ela não desune

Não existe `split`. Não existe `desunir`. Não existe remover uma aresta. E isso não é preguiça de quem implementou: é **estrutural**. O path compression destrói a história. Depois que a árvore foi achatada, a informação de quem estava pendurado em quem (e por causa de qual aresta) simplesmente não existe mais. Foi exatamente essa destruição que comprou o α(n).

Quando o seu problema tem remoção, restam três saídas.

**Inverta o tempo.** Se todas as remoções são conhecidas de antemão, processe a entrada de trás para frente: remoção lida ao contrário **é** inserção. O exemplo canônico é o LeetCode 803, *Bricks Falling When Hit*. Ele pede quantos tijolos caem a cada martelada, e "cair" é "deixar de estar conectado ao teto": uma pergunta de conectividade com remoção, o pesadelo do DSU. A inversão resolve: apague **todos** os tijolos que serão atingidos, monte o Union-Find do que sobrou, e então devolva os tijolos um a um na ordem inversa, medindo quanto o grupo do teto cresce a cada devolução. Cada devolução é uma união, e o problema difícil virou o problema fácil.

**Use DSU com rollback.** Union by rank **sem** path compression, guardando numa [pilha](/topico/pilhas) o que cada união mudou, permite desfazer a última união em O(1). O custo por operação sobe para O(log n), porque sem compressão a árvore continua com altura logarítmica. As duas técnicas são incompatíveis por construção: compressão é o que apaga o histórico, rollback é o que precisa dele.

**Aceite que o problema é outro.** Conectividade dinâmica com remoção **online** (sem conhecer o futuro) é um problema genuinamente mais difícil, resolvido por estruturas bem mais pesadas na casa de O(log² n) amortizado. Se o seu caso é esse, Union-Find é a ferramenta errada e insistir nele só adia a conversa.

Vale registrar mais uma coisa que a estrutura **não** entrega: ela responde "sim, mesmo grupo", mas nunca diz **por onde**. Não existe caminho, não existe distância, não existe menor rota. Para isso você volta ao [DFS/BFS](/topico/dfs-bfs) ou ao [Dijkstra](/topico/dijkstra). E note que essa amnésia é justamente o que a deixa tão barata.

## As armadilhas que pegam todo mundo

**Comparar pais em vez de raízes.** `if pai[a] == pai[b]` parece razoável e está errado: dois elementos do mesmo grupo podem estar pendurados em pais diferentes, a três níveis um do outro. A única pergunta válida é `find(a) == find(b)`. Este é o bug número um, e ele passa nos casos pequenos. O primo dele é usar `pai[x] == x` como teste de grupo: esse teste significa exatamente "x é a raiz do grupo dele", nada além. Não diz de que grupo, não compara nada com ninguém.

**Misturar rank com size no meio do caminho.** Escolha um dos dois e vá até o fim. O híbrido que aparece em código copiado de dois lugares diferentes é este:

```python
    if rank[ra] < rank[rb]:        # compara por altura...
        ra, rb = rb, ra
    pai[rb] = ra
    tamanho[ra] += tamanho[rb]     # ...e atualiza o tamanho. O rank nunca sobe.
```

O `rank` fica congelado em zero, a decisão de quem entra embaixo de quem vira sorteio, e a altura volta a crescer sem controle. O código roda, passa nos testes pequenos e estoura o tempo no teste grande.

**Ler `tamanho[x]` sem chamar `find`.** O erro mais silencioso da lista: fora da raiz, esse array guarda um número obsoleto, e obsoleto não é absurdo: é um tamanho plausível, de um grupo que existiu. Sempre `tamanho[find(x)]`.

**Índice base 0 contra base 1.** Metade dos enunciados numera os vértices de 1 a n. Se você fizer `UnionFind(n)` e chamar `unir(n, 1)`, o resultado é `IndexError` na melhor das hipóteses. Aloque `n + 1` e ignore a posição 0, ou subtraia 1 de todo mundo na entrada. O que não dá para fazer é decidir no meio.

**Decrementar o contador de componentes sempre.** O contador só cai quando a união **de fato** aconteceu:

```python
    dsu.unir(u, v)
    componentes -= 1          # ERRADO: a aresta pode ter sido redundante

    if dsu.unir(u, v):
        componentes -= 1      # certo: só conta quando duas árvores viraram uma
```

É por isso que o `unir` deste artigo devolve `bool`. Sem ele, você reimplementa a mesma comparação de raízes do lado de fora, e uma hora esquece.

**Esquecer que `find` escreve.** Ele parece uma consulta e é uma mutação: path compression reescreve o array `pai`. Numa estrutura compartilhada entre threads isso é uma corrida de dados esperando acontecer, e num contexto que assume imutabilidade é uma surpresa desagradável.

**Não ordenar antes do Kruskal.** O Union-Find não tem opinião sobre pesos. Alimentado com arestas fora de ordem, ele devolve alegremente uma árvore geradora qualquer, que é conexa, acíclica e não é mínima. O bug não levanta exceção nenhuma.

## Como praticar

Escreva a classe de memória, sem olhar, umas três vezes ao longo de uma semana. Ela é curta o bastante para isso e frequente o bastante para valer a pena. Em prova cronometrada, digitá-la em dois minutos muda o jogo.

Depois quebre a sua implementação com um **espelho**: uma versão burra, obviamente correta, e milhares de operações sorteadas comparando as duas a cada passo.

```python
import random

random.seed(7)
n = 60
dsu, rotulo = UnionFind(n), list(range(n))     # o espelho: um rótulo por elemento
for _ in range(5000):
    a, b = random.randrange(n), random.randrange(n)
    if random.random() < 0.3:
        assert dsu.conectado(a, b) == (rotulo[a] == rotulo[b])
    else:
        antigo, novo = rotulo[a], rotulo[b]
        assert dsu.unir(a, b) == (antigo != novo)
        rotulo[:] = [novo if r == antigo else r for r in rotulo]   # O(n), de propósito
    assert dsu.componentes == len(set(rotulo))
    assert dsu.tamanho_do_grupo(a) == rotulo.count(rotulo[a])
```

Repare na piada embutida: o espelho é exatamente a "segunda ideia" da primeira seção, aquela que reetiqueta o array inteiro a cada união. Ela é lenta demais para usar e simples demais para errar, e é por isso que serve de referência.

Uma ordem de estudo que funciona: comece pelo 547 (*Number of Provinces*), que é só contar componentes; vá para o 684 (*Redundant Connection*), que é o `unir` devolvendo `False`; depois o 990 (*Satisfiability of Equality Equations*), para fixar a ideia de processar todas as igualdades antes das desigualdades; então o 721 (*Accounts Merge*), onde o trabalho de verdade é mapear string para índice antes de o DSU entrar; o 1584 (*Min Cost to Connect All Points*), que é Kruskal completo; e só no fim o 803 (*Bricks Falling When Hit*), para praticar a inversão do tempo.

Em cada um deles, faça a pergunta que separa quem entendeu de quem decorou: **qual é a relação de equivalência aqui, e qual é o elemento?** No 721 o elemento é o e-mail, não a conta. No 803 o elemento é a célula da grade, mais um nó virtual para o teto. Acertar essa escolha é 80% da solução; o resto é a classe que você já sabe de cor.
